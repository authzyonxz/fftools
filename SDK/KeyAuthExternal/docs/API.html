O cliente não recebe um packageId editável. O servidor resolve o pacote EXTERNAL usando o proprietário configurado por KEYAUTH_OWNER_ID e confere o pacote da licença. O cliente também exige os identificadores acima no JWT assinado. Uma key de outro pacote deve ser recusada, mesmo que esteja ativa.

O ID numérico observado no MySQL é 2. Ele pertence ao banco atual; não substitui o UUID público usado no protocolo v2 e não deve ser presumido após migrações.

Três credenciais distintas: o token da biblioteca Logos, o Bearer administrativo wqd_… e o token temporário de sessão v2 não são intercambiáveis. O login deste SDK usa a key do usuário e uma sessão v2; nenhum segredo administrativo é embutido.

02 / Fluxo de licença para o IPA

Key → sessão EXTERNAL → prova da instalação → desafio de autorização → JWT ES256 → assinatura + claims → introspecção online → entrada no app

Transporte atual: JSON sobre HTTPS. A autorização é um JWT assinado, não um envelope AES. Assinatura assegura autenticidade, mas não oculta o conteúdo; o JWT atual contém a key em seus claims. Não registre JWT, key ou sessão em logs, analytics ou relatórios de crash.

Formato das respostas

{"ok":true,"data":{"completed":true},"error":null}

{"ok":false,"data":null,"error":{"code":"KEY_EXPIRED","message":"KEY_EXPIRED"}}

Sucesso normalmente usa HTTP 200; erros do protocolo geralmente usam 400, método não permitido 405, rota desconhecida 404 e banco indisponível 503. O cliente trata 429 e falhas de rede sem liberar acesso. ok:true ou HTTP 200 isoladamente não bastam.

Identidade e assinatura da instalação

  • Chave P-256 criada no Secure Enclave. A chave privada não é exportada pelo SDK.
  • Chave pública: formato X9.63 não comprimido, 65 bytes: 04 || X(32) || Y(32), codificado em base64url sem padding.
  • installationId deste SDK: base64url(SHA256(publicKeyRaw)). É estável enquanto a chave protegida e o acesso ao Keychain forem preservados.
  • Assinar os bytes UTF-8 exatos de canonical, sem reconstruir ou reordenar JSON.
  • A assinatura do desafio usa ECDSA SHA-256 em DER/X9.62, depois base64url. No JWT ES256, a assinatura recebida é R || S, 64 bytes; o verificador converte para DER antes de chamar Apple Security.
  • Antes de assinar, o SDK confere purpose, pacote, instalação, challengeId, challenge, sessionHash e validade do desafio.
// Campos típicos de canonical (a ordem real vem do servidor):
{"purpose":"authorization","package":"external1",
 "challengeId":"…","challenge":"…","installationId":"…",
 "sessionHash":"base64url(SHA256(tokenDaSessao))"}

Validade e manutenção

A key começa a vencer na primeira validação aceita pelo servidor, e fica vinculada ao dispositivo. Reset de HWID não renova prazo. Pausa da key não congela tempo. Pacote pausado bloqueia emissão e revalidação. A sessão e o grant duram no máximo 300 segundos; o desafio dura 120 segundos. Não existe endpoint de refresh: inicie um novo fluxo quando a sessão vencer.

Unidades: expiresAt de sessão/desafio/grant usa segundos Unix. activatedAt e expiresAt de data.license na introspecção usam milissegundos Unix. O expiresAt da validação legada é uma string ISO-8601.

Verificação local do JWT

O SDK exige assinatura válida pela chave pública fixada, algoritmo ES256, typ KA2+jwt, kid conhecido, issuer, audience, pacote, UUID, instalação, sessionHash, status ativo, policyVersion 2, scope app:open, iat/exp numéricos e prazo máximo de cinco minutos. Campos crit não reconhecidos são recusados. Após isso, o servidor precisa confirmar a sessão e a licença; a resposta de introspecção deve corresponder aos claims assinados.

A chave pública foi extraída da VPS em 27/11/2026. Não é segredo. Na rotação da chave do servidor, publique uma atualização com o novo kid/chave; planeje uma janela de rotação. Não busque uma chave arbitrária da própria resposta que deseja validar.

03 / API AES-256-GCM existente

Uso administrativo ou backend. POST /api/v1/command exige token wqd_… que também pode administrar keys. Ofuscá-lo dentro do IPA não transforma esse token em credencial segura para distribuição. Nem toda resposta é criptografada. Ausência/token inválido: HTTP 401 com {"error":"unauthorized"}. Limite: 429 com rate_limited. Envelope inválido e exceções internas: 400 com invalid_encrypted_request. Comando inválido após decifrar: 400 com envelope contendo ok:false e result.error=invalid_request. Não tente decifrar um erro JSON sem os campos do envelope.

C++ e Objective-C++

// C++17, servidor/ferramenta controlada; OpenSSL 3:
#include "Transport.hpp"
auto envelope = keyauth::encrypt(jsonUTF8, apiToken);
// Serialize version/algorithm/iv/ciphertext/tag em JSON e envie via HTTPS.
// Na resposta, valide HTTP e o formato antes de construir Envelope.
auto jsonResponse = keyauth::decrypt(envelopeRecebido, apiToken);
// Parse JSON e exija result.valid == true; não basta a decifragem funcionar.

// Objective-C++, opcional:
NSDictionary *body = [KACommandCodec encryptCommand:command token:serverToken error:&error];
NSDictionary *decoded = [KACommandCodec decryptEnvelope:response token:serverToken error:&error];

O codec não implementa HTTP nem concede acesso ao app. Use um cliente HTTPS com validação de certificado, timeout e redirects desabilitados para evitar vazamento do Bearer. Em iOS, esse adaptador requer OpenSSL compilado para a plataforma; a Apple não fornece essa dependência ao target automaticamente. O fluxo v2 incluído não depende de OpenSSL.

O envelope atual não contém timestamp, ID de requisição, AAD ou cache de nonces. AES-GCM detecta adulteração, mas não impede replay de uma mensagem válida. Um futuro protocolo AES para o app deve usar credenciais limitadas à licença e proteção de replay no servidor; não reutilize o endpoint administrativo como login móvel.

Na API legada, result.reason pode ser invalid_key, package_mismatch, package_paused, key_paused, expired, device_mismatch ou ok. O endpoint v2 mapeia parte dessas causas para KEY_INVALID. Uma mensagem de “key banida” exigiria suporte real no servidor; o schema atual possui active/paused.

05 / Tela sofisticada e entrada no app

Visual

Preto e branco, fundo orbital desenhado em UIKit, cartão arredondado, tipografia adaptativa, campo protegido e botão de entrada.

Experiência

Rolagem com teclado, VoiceOver, mensagem de erro no formulário, bloqueio de envios duplicados e animação curta respeitando Reduzir Movimento.

Liberação

O controlador principal só é instanciado após validação completa. Sem booleano persistido de “licença válida”.

#import "KALicenseViewController.h"

KAProtectedRootController *gate = [[KAProtectedRootController alloc]
  initWithContentFactory:^UIViewController *(KAExternalClient *client, NSDictionary *license) {
    YourMainViewController *main = [YourMainViewController new];
    main.licenseClient = client;
    return main;
  }];
self.window.rootViewController = gate;
[self.window makeKeyAndVisible];

// Antes de uma operação protegida, também em um arquivo .mm:
[self.licenseClient revalidate:^(NSDictionary *license, NSError *error) {
  if (error) return;
  // Chame sua implementação Objective-C ou C++ aqui.
}];

YourMainViewController é o controlador do seu projeto, não uma classe fornecida. Veja ios/IntegrationExample.txt. Instale somente um coordenador de autenticação: este fluxo substitui a integração anterior quando você decidir migrar, sem editar o SDK Logos. A implantação no IPA atual não foi realizada por este pacote.

O gate bloqueia ao perder atividade, descarta o grant e volta ao login. Enquanto o app está aberto, revalida a cada 30 segundos; antes de cada operação protegida, faça outra revalidação. Após cinco minutos, o fluxo atual pede nova entrada; uma key salva pode ser reutilizada deixando o campo vazio. O conteúdo pode permanecer visível até a próxima verificação após uma revogação; o servidor deve impedir imediatamente os recursos protegidos.

Keychain e assinatura

A opção de salvar grava a key somente após a validação, como generic password, com WhenUnlockedThisDeviceOnly e sem sincronização iCloud. O grant e o token da sessão ficam só em memória. A identidade usa uma chave Secure Enclave persistente. Falhas de Keychain não provocam fallback para UserDefaults ou arquivos.

Requisitos: iOS 15+, ARC, UIKit/Foundation/Security e aparelho com Secure Enclave. O simulador não recebe um bypass de segurança. A assinatura precisa permitir o acesso correto ao Keychain; mudar Bundle ID, equipe ou entitlements pode perder a identidade e exigir reset de HWID. Atributos ThisDeviceOnly impedem migração para outro dispositivo, mas não equivalem a apagar dados ao desinstalar.

06 / Proteções e limites honestos

Incluído no cliente

  • Verificação criptográfica ES256 e EXTERNAL fixo; rejeição de assinatura, pacote, sessão, política e prazo incorretos.
  • Chave privada Secure Enclave, Keychain por aparelho e ausência de token administrativo embutido.
  • HTTPS com validação padrão do sistema, sessão efêmera e redirects bloqueados no login.
  • Sem autorização offline e sem flag de acesso em preferências; falha de rede mantém bloqueado.
  • Prazo também acompanhado com relógio monotônico durante o processo; retorno do background exige novo fluxo.
  • Configuração Release com símbolos privados, dead stripping, LTO e dSYM separado. Isso reduz informações expostas; não oculta todos os nomes do runtime Objective-C.

cpp/PublicLiteral.hpp inclui ofuscação opcional de literais públicos, como rótulos, em C++/Objective-C++: auto label = KA_PUBLIC_LITERAL("EXTERNAL");. É uma transformação XOR simples para dificultar buscas triviais de strings, não criptografia nem proteção de segredo. O texto é recuperável em memória. O cliente principal mantém identificadores de protocolo legíveis para auditoria; não afirma que URLs, metadados Objective-C ou chaves públicas ficaram ocultos.

O que precisa ser reforçado no servidor

  1. Vincular instalação à chave pública. Hoje o servidor aceita installationId e publicKey enviados pelo cliente, sem cadastro persistente ligando os dois. O SDK deriva o ID da chave, mas um cliente alterado não é obrigado a seguir essa regra. O servidor deve verificar essa derivação ou persistir a associação de forma imutável.
  2. Congelar enrollment. Não permitir substituir publicKey/installationId após enrollment, nem reutilizar desafios em operações concorrentes. Consumir o desafio atomicamente.
  3. Proteger cada download/ação. /3106/api/catalog e /3106/f/*.fpp são públicos. Sua criptografia AES-CBC+HMAC é proteção de conteúdo, não autorização individual. Um segredo compartilhado distribuído no app pode ser extraído.
  4. Limitar requisições e limpar sessões. Aplicar rate limit por IP/sessão/dispositivo e expiração periódica; usar armazenamento adequado se houver múltiplos processos.
  5. Reduzir exposição dos grants. Substituir key em texto por referência opaca de licença; incluir escopos mínimos e, quando necessário, prova assinada por requisição para reduzir replay de Bearers roubados.
  6. App Attest. Validar atestados e assertions no backend com desafio e contador. Não basta chamar uma API Apple no cliente. Confirmar disponibilidade e compatibilidade com a distribuição e assinatura utilizadas; não fingir que está ativo em qualquer IPA reassinado.
  7. API administrativa. Unificar permissões do painel e /api/v1/command, corrigir cookie Secure, revogação de sessão e erros de negócio. Não conceder esses poderes ao token do app.
Nenhuma ofuscação, detecção de hook ou verificação local impede toda alteração em dispositivo comprometido. Não foi adicionado código para derrubar o app, esconder processos ou confiar em detecção de jailbreak. A barreira principal é a autorização no servidor. Operações totalmente locais continuam sujeitas a patch, mesmo com login robusto.

Esses reforços de backend são requisitos recomendados, não alterações implantadas. A documentação não afirma que o servidor atual fornece App Attest, proteção de replay por requisição ou AES no endpoint v2.

07 / Validação e publicação

Execute em macOS com Xcode e OpenSSL 3:

bash tests/validate-ios.sh
  • Compila todos os .m para arm64/iOS 15 e o adaptador .mm.
  • Compara criptografia e decifragem Node.js ↔ C++ com dados sintéticos.
  • Rejeita alteração de IV, ciphertext, tag, token incorreto e entradas malformadas.
  • Testa verificação ES256 pela Apple Security com chave efêmera de teste; o código distribuído não contém um modo de bypass.
  • Testa pacote, UUID, issuer, audience, instalação, sessão, prazo, escopo, algoritmo, kid e assinatura inválidos.

Consulte VALIDATION.txt para o resultado final. Compilação e testes de protocolo não substituem teste de interface, Secure Enclave, Keychain e ciclo de vida em iPhone assinado. Não foram criadas keys de produção nem alterados créditos para testar.
